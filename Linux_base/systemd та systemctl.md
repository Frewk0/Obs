
# 📖 Повний гайд з systemd та systemctl для DevOps

## 1. Що таке systemd і НАВІЩО він потрібен?

**`systemd`** — це системний ініціалізатор (Init System) та менеджер служб у більшості сучасних дистрибутивів Linux (Ubuntu, Debian, CentOS, RHEL, Fedora, Rocky Linux).

  

### 💡 Логіка та історія

Коли сервер вмикається і завантажується ядро Linux (Kernel), воно запускає найперший процес у системі з **PID 1** (Process ID = 1).

У старих системах цим процесом був `SysVinit` чи `Upstart`. Вони запускали служби послідовно (одна за одною), що було повільно, не гнучко і складно для відстеження.

  

На зміну їм прийшов **`systemd`**:

  

1. Він стає **PID 1** у системі.
    
      
    
2. Він керує всіма іншими процесами, демонами (services), фоновими задачами, мережею, замонтованими дисками та логами.
    
      
    
3. Він запускає сервіси **паралельно**, що робить завантаження сервера миттєвим.
    
      
    
4. Якщо процес падає — `systemd` автоматично його перезапускає.
    
      
    

## 2. Поняття Unit (Юніт)

Усе, чим керує `systemd`, називається **Unit (юніт)**. Юніти описуються у звичайних текстових конфігураційних файлах.

  

### 📌 Основні типи юнітів:

- **`.service`** — найважливіше для DevOps. Це фоновий демон чи програма (Nginx, Docker, PostgreSQL, твій власний Python-скрипт).
    
      
    
- **`.timer`** — аналог `cron`. Запускає певний `.service` за розкладом чи таймером.
    
      
    
- **`.target`** — група юнітів для досягнення певного стану системи (наприклад, `multi-user.target` — звичайний консольний режим, `graphical.target` — графічний інтерфейс).
    
      
    
- **`.mount` / `.automount`** — монтування файлових систем та дисків.
    
      
    
- **`.socket`** — мережевий сокет, який `systemd` слухає і запускає відповідний сервіс при появі трафіку.
    
      
    

## 3. Команда `systemctl` — Головний інструмент керування

**`systemctl`** — це консольна утиліта для взаємодії з `systemd`. Вона дозволяє запускати, зупиняти, перезапускати сервіси, дивитися їхній статус та перевіряти автозавантаження.

  

### 🚀 Основні команди керування сервісами:

|**Команда**|**Що робить**|**Пояснення**|
|---|---|---|
|`systemctl start nginx`|**Запускає** сервіс|Запускає демон прямо зараз у оперативній пам'яті.|
|`systemctl stop nginx`|**Зупиняє** сервіс|М'яко завершує роботу процесу прямо зараз.|
|`systemctl restart nginx`|**Перезапускає** сервіс|Повною мірою зупиняє і запускає наново (у процесу змінюється PID).|
|`systemctl reload nginx`|**Перезавантажує конфіг**|Перечитує налаштування _без зупинки_ процесу (PID не змінюється, немає downtime).|
|`systemctl status nginx`|**Виводить статус**|Показує: працює чи ні, PID, використання пам'яті та останні логи.|

### 🔄 Керування Автозавантаженням (Enable / Disable)

> ⚠️ **Критично важливо зрозуміти різницю між `start` та `enable`:**
> 
>   
> 
> - `start` / `stop` — впливають на сервіс **ПРЯМО ЗАРАЗ** (у поточній сесії).
>     
>       
>     
> - `enable` / `disable` — визначають, чи запуститься сервіс **ПІСЛЯ ПЕРЕЗАВАНТАЖЕННЯ СЕРВЕРА**.
>     
>       
>     

|**Команда**|**Що робить**|
|---|---|
|`systemctl enable nginx`|Додає сервіс в автозавантаження під час старту ОС (створює симлінк у `/etc/systemd/system/`).|
|`systemctl disable nginx`|Видаляє сервіс з автозавантаження.|
|`systemctl enable --now nginx`|**Лайфхак:** одночасно вмикає автозавантаження (`enable`) і запускає сервіс прямо зараз (`start`).|
|`systemctl is-active nginx`|Повертає `active` або `inactive` (зручно для використання у Bash-скриптах).|
|`systemctl is-enabled nginx`|Повертає `enabled` або `disabled`.|

## 4. Як правильно читати `systemctl status`

Коли ти вводиш `systemctl status docker`, ти бачиш вивід на кшталт цього:

  

Plaintext

```
● docker.service - Docker Application Container Engine
     Loaded: loaded (/lib/systemd/system/docker.service; enabled; vendor preset: enabled)
     Active: active (running) since Fri 2026-08-07 10:00:00 EEST; 3h ago
       Docs: https://docs.docker.com
   Main PID: 1234 (dockerd)
      Tasks: 12
     Memory: 45.2M
        CPU: 1.2s
     CGroup: /system.slice/docker.service
             └─1234 /usr/bin/dockerd -H fd://
```

### 🔍 На що дивитися DevOps-інженеру:

1. **`Loaded:`** — показує, де лежить файл конфігурації юніта і чи увімкнено автозавантаження (`enabled`).
    
      
    
2. **`Active:`**
    
      
    - `active (running)` — все супер, працює.
        
          
        
    - `active (exited)` — процес виконав дію і успішно завершився (нормально для одноразових скриптів).
        
          
        
    - `inactive (dead)` — зупинено.
        
          
        
    - `failed` — **ПОМИЛКА!** Процес упав або не зміг запуститися.
        
          
        
3. **`Main PID:`** — номер головного процесу в системі.
    
      
    
4. **`Memory / CPU:`** — ресурси, які споживає сервіс.
    
      
    
5. **Останні рядки нижче:** — шматочок логів з `journald` (відразу видно, якщо сталася помилка під час старту).
    
      
    

## 5. Анатомія файл-юніта: Як створити ВЛАСНИЙ `.service`

У DevOps постійно виникає задача: _"Є Python-скрипт або Go-бінарник. Зроби так, щоб він працював як демон у фоні 24/7 і перезапускався при падінні"_.

  

### 📂 Де лежать файли юнітів:

1. `/lib/systemd/system/` або `/usr/lib/systemd/system/` — системні юніти (встановлені через `apt`/`yum`). **Їх краще не редагувати вручну!**
    
      
    
2. `/etc/systemd/system/` — **НАШЕ МІСЦЕ!** Сюди DevOps кладе власні юніти або кастомні конфіги. Вони мають вищий пріоритет.
    
      
    

### 📝 Структура файлу `/etc/systemd/system/myapp.service`:

Ini, TOML

```
[Unit]
Description=My Custom Python App
After=network.target postgresql.service
Wants=postgresql.service

[Service]
Type=simple
User=appuser
WorkingDirectory=/opt/myapp
ExecStart=/opt/myapp/venv/bin/python main.py
Restart=always
RestartSec=5
Environment="PORT=8080" "ENV=production"

[Install]
WantedBy=multi-user.target
```

### 🧩 Розбір секцій та ключових параметрів:

#### 1. Секція `[Unit]` (Метадані та залежності)

- **`Description`** — зрозумілий опис сервісу.
    
      
    
- **`After`** — порядок запуску. `After=network.target` означає _"запусти мій сервіс ТІЛЬКИ ПІСЛЯ того, як підніметься мережа"_.
    
      
    
- **`Requires`** — жорстка залежність. Якщо вказаний сервіс не запуститься, мій сервіс навіть не намагатиметься стартувати.
    
      
    
- **`Wants`** — м'яка залежність. Намагатиметься запустити вказаний сервіс, але якщо той впаде — мій все одно спробує запуститися.
    
      
    

#### 2. Секція `[Service]` (Як запускати і контролювати)

- **`Type`**:
    
      
    - `simple` _(за замовчуванням)_ — процес, вказаний в `ExecStart`, є головним.
        
          
        
    - `forking` — процес породжує дочірній процес у фоні (як класичний Nginx).
        
          
        
- **`User` / `Group`** — від імені якого користувача запускати (ніколи не запускай додатки від `root` з міркувань безпеки!).
    
      
    
- **`WorkingDirectory`** — робоча директорія перед виконанням команди.
    
      
    
- **`ExecStart`** — абсолютний шлях до команди або бінарника, який треба запустити.
    
      
    
- **`ExecReload`** — команда для перезавантаження конфігу (наприклад, `kill -HUP $MAINPID`).
    
      
    
- **`Restart`**:
    
      
    - `always` — перезапускати ЗАВЖДИ (якщо впав, відпрацював чи був вбитий).
        
          
        
    - `on-failure` — перезапускати ТІЛЬКИ якщо процес завершився з помилкою (код відповіді не 0).
        
          
        
- **`RestartSec`** — пазуа (у секундах) перед наступною спробою перезапуску.
    
      
    
- **`Environment`** / **`EnvironmentFile`** — змінні оточення (ENV) або шлях до `.env` файлу.
    
      
    

#### 3. Секція `[Install]` (Як вмикати в автозавантаження)

- **`WantedBy=multi-user.target`** — стандартне значення для звичайних сервісів. Означає, що сервіс стартуватиме при нормальному завантаженні системи у консольному режимі.
    
      
    

## 6. Золотий алгоритм створення власного сервісу

Коли ти створив або змінив файл у `/etc/systemd/system/myapp.service`:

  

1. **Обов'язково сповісти `systemd` про новий файл:**
    
      
    
    Bash
    
    ```
    systemctl daemon-reload
    ```
    
    _(Без цього `systemd` не побачить твоїх змін у файлі!)_
    
      
    
2. **Запусти сервіс:**
    
      
    
    Bash
    
    ```
    systemctl start myapp
    ```
    
3. **Перевір статус:**
    
      
    
    Bash
    
    ```
    systemctl status myapp
    ```
    
4. **Якщо все працює — додай в автозавантаження:**
    
      
    
    Bash
    
    ```
    systemctl enable myapp
    ```
    

## 7. Робота з логами: `journald` та `journalctl`

`systemd` має власний вбудований модуль логування — **`systemd-journald`**. Він автоматично збирає `stdout` (стандартний вивід) та `stderr` (помилки) з усіх сервісів.

  

Для читання логів використовується утиліта **`journalctl`**.

  

### 📋 Шпоргалка з `journalctl` для DevOps:

Bash

```
# 1. Подивитися логи конкретного сервісу
journalctl -u myapp

# 2. Логи в режимі реального часу (як tail -f) — НАЙЧАСТІШЕ
journalctl -u myapp -f

# 3. Вивести останні N рядків логу
journalctl -u myapp -n 50

# 4. Показувати логи ТІЛЬКИ з моменту останнього завантаження сервера
journalctl -u myapp -b

# 5. Фільтрація за часом
journalctl -u myapp --since "1 hour ago"
journalctl -u myapp --since "2026-08-07 10:00:00" --until "2026-08-07 12:00:00"

# 6. Показувати тільки помилки (Priority: err, critical, alert)
journalctl -u myapp -p err
```

У виводі `systemctl enable` ти побачив створення `symlink` (ярлика). Саме так systemd додає програми в автозапуск — він створює посилання на твій файл у спеціальній папці `multi-user.target.wants`, яку читає при завантаженні ОС.

### Відповідь на питання про `disable`


1. **Чистота стану (State Hygiene):** `systemctl disable` — це команда для `systemd` офіційно прибрати сервіс з ланцюжка залежностей. Якщо ти просто видалиш файл, у системі може залишитися "битий" лінк, на який systemd буде видавати попередження при кожному `daemon-reload` або завантаженні (що засмічує логи й відволікає).
    
2. **Безпека та логіка:** В деяких системах, якщо ти спочатку видалиш файл, а потім спробуєш зробити `disable`, `systemctl` видасть помилку, бо файл конфігу вже не існує. Завжди краще спочатку "вимкнути" сервіс (зупинити логіку), а потім видаляти його "фізичне тіло".
    

### Відповідь на інтерв'ю (Crash Loop)

Тепер щодо твого питання про "вічний цикл" падінь. Ти правий: `Restart=always` без запобіжників — це справжня загроза для сервера. Якщо процес падає миттєво, CPU буде завантажений на 100% не самим процесом, а постійним створенням/знищенням процесів через `systemd`.

**Але systemd — це не дурна програма.** У нього є вбудований запобіжник:

- Якщо сервіс падає занадто часто (стандартно — більше 5 разів за 10 секунд), `systemd` переводить його в стан **`failed`** (або `start-limit-hit`) і **припиняє спроби перезапуску**.
    
- Система каже: _"Я бачу, що цей сервіс зламаний, я не буду палити ресурси сервера, виправте код, а потім самі його запустіть"_.
    

Це називається **Start Limit**. Це вбудований захист, щоб не "покласти" весь сервер через один кривий скрипт.
