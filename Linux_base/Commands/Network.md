## 1. Бізнес-контекст та Архітектура (Як Linux бачить мережу)

Уяви: ти розгорнув базу даних і вебсервер. Сервіс "лежить", клієнти скаржаться. Розробник каже: _"Це проблема з сервером, мій код працює"_. Твоя задача як DevOps — за хвилину локалізувати проблему. Що саме зламалося? Немає інтернету? Відвалився DNS? Закритий порт бази даних? Без базових утиліт діагностики мережі ти просто граєш у вгадування. Мережеві команди — це твій стетоскоп.

Щоб налаштовувати мережу, треба розуміти її базові сутності:

- **Інтерфейси (Interfaces):** Твої віртуальні або фізичні "мережеві картки". `lo` (Loopback, `127.0.0.1`) — інтерфейс для спілкування програм усередині сервера. `eth0`, `ens33` або `wlan0` — інтерфейси, які дивляться у зовнішній світ.
    
- **Маршрути (Routes):** Таблиця в ядрі, яка вказує пакету куди летіти, якщо адресат не в локальній мережі. Головний маршрут — _Default Gateway_ (шлюз за замовчуванням).
    
- **Порти та Сокети:** IP-адреса приводить пакет до сервера. Порт (1-65535) — це "двері" конкретної програми на цьому сервері. Стан `LISTEN` означає, що програма відкрила двері і чекає на підключення.
    

### Стек TCP/IP (DevOps Deep Dive)

Дані перед відправкою загортаються як матрьошка.

- **L3 (Мережевий рівень):** Протокол IP. Його єдина задача — доставити пакет від точки А до точки Б. Він не перевіряє, чи дійшов пакет успішно.
    
- **L4 (Транспортний рівень) 🟥 MUST KNOW:** Вирішує, _як саме_ передавати дані через порти (TCP або UDP).
    
- **L7 (Прикладний рівень) 🟨 SHOULD KNOW:** Мови, якими програми спілкуються поверх TCP/UDP (HTTP/HTTPS - 80/443, DNS - 53, SSH - 22, SMTP - 25/587).
    

### TCP vs UDP (Найважливіше на співбесіді)

- **TCP (Надійність):** Протокол із підтвердженням доставки. Використовує _Three-way Handshake_ (SYN $\rightarrow$ SYN-ACK $\rightarrow$ ACK). Якщо пакет губиться, він відправляється повторно. Гарантує правильний порядок. Працює повільніше. _DevOps Use Cases:_ HTTP, SSH, Бази даних (втрата байта ламає файл).
    
- **UDP (Швидкість):** Протокол без гарантій. Просто стріляє пакетами, не помічаючи втрат. Забезпечує мінімальну затримку (low latency). _DevOps Use Cases:_ DNS (запит має бути миттєвим), відеострімінг, онлайн-ігри, відправка метрик.
    

## 2. Локальна Мережа та Специфічні Нюанси ОС

### Junior DevOps Lab: "127.0.0.1 vs 0.0.0.0"

Питання зі співбесіди: у чому різниця між тим, коли сервіс слухає `127.0.0.1` і `0.0.0.0`?

- **`127.0.0.1` (Localhost):** Приймати підключення ТІЛЬКИ зсередини цього ж комп'ютера. Стандарт безпеки для баз даних. З інтернету доступу немає.
    
- **`0.0.0.0` (Any IPv4):** Приймати підключення звідусіль (відкрито для всього світу або локальної мережі, як SSH чи веб-сервер).
    

### Архітектура серверів та поведінка ядра

- **Loopback та Firewall:** Фаєрволи (`ufw`, `iptables`) за замовчуванням мають приховане правило, яке повністю довіряє трафіку на `lo`. Якщо ти заблокував порт (`ufw deny 8000`), перевіряти його через `curl localhost:8000` не можна — запит пройде. Тестуй із зовнішнього IP.
    
- **Broadcast-адреси (.255):** IP типу `192.168.0.255` у підмережі `/24` розсилає пакети всім пристроям. TCP-з'єднання з нею неможливе, бо TCP вимагає зв'язку "один до одного" (Unicast). Запит миттєво відхиляється.
    
- **Лінійні vs Server Loop:** Лінійні утиліти (`nc -l -p 8080`) приймають одне з'єднання, виводять дані і вмирають. Реальні сервери (Nginx, Python) працюють у нескінченному циклі (`while True`), закриваючи поточну сесію, але продовжуючи слухати порт.
    
- **IPv6 Fallback:** У `/etc/hosts` часто є два записи для localhost: `127.0.0.1` (IPv4) та `::1` (IPv6). Сучасні утиліти (`curl`) спочатку пробують IPv6. Якщо сервер слухає тільки IPv4, ядро відхиляє запит, і утиліта миттєво робить Fallback на IPv4.
    

## 3. Netfilter, NAT та Обмеження доступу (Firewall)

В ядрі Linux є модуль **Netfilter**. Це справжній фаєрвол. Ані `iptables`, ані `ufw` самі по собі пакети не фільтрують — вони лише передають правила у Netfilter.

Netfilter складається з **5 блокпостів (Chains)**: `PREROUTING`, `INPUT` (до нашого сервера), `FORWARD` (через наш сервер), `OUTPUT` (від нашого сервера), `POSTROUTING`.

Архітектура iptables має 3 сутності:

1. **Таблиці (Tables):** Filter (блокування), NAT (зміна IP/портів), Mangle (зміна заголовків).
    
2. **Ланцюги (Chains):** Етап, на якому ловиться пакет.
    
3. **Дії (Targets):** `ACCEPT` (пропустити), `DROP` (знищити мовчки), `REJECT` (відхилити з повідомленням про помилку).
    

### Що таке NAT?

NAT підміняє IP-адреси "на льоту". Для запам'ятовування з'єднань ядро використовує модуль пам'яті `nf_conntrack`. Правила NAT застосовуються ТІЛЬКИ до першого пакета сесії (стан `NEW`).

- **SNAT / Masquerade:** Працює у `POSTROUTING`. Підміняє IP відправника (дозволяє контейнерам виходити в інтернет). `iptables -t nat -A POSTROUTING -o eth0 -j MASQUERADE`
    
- **DNAT / Port Forwarding:** Працює у `PREROUTING`. Підміняє IP/Порт отримувача (прокидання портів Docker). `iptables -t nat -A PREROUTING -p tcp --dport 80 -j DNAT --to-destination 172.17.0.2:8080`
    

### Команди UFW (MUST KNOW)

Працює за принципом "Заборонити все, що не дозволено явно".

Bash

```
sudo ufw reset                  # Скинути до заводських налаштувань
sudo ufw default deny incoming  # Блокувати всі вхідні (найкраща практика)
sudo ufw default allow outgoing # Дозволити серверу виходити в інтернет
sudo ufw allow 22/tcp           # КРИТИЧНО! Зробити ДО включення ufw
sudo ufw enable                 # Увімкнути firewall
sudo ufw status numbered        # Перевірити статус та номери правил

# Реальний сценарій: Дозволити доступ до БД (5432) тільки для application-сервера
sudo ufw deny 5432
sudo ufw allow from 10.0.0.10 to any port 5432
```

### Команди iptables (SHOULD KNOW)

Правила читаються згори донизу. Щойно пакет збігається з правилом — перевірка зупиняється.

Bash

```
sudo iptables -L -n -v          # Поточні правила (-L список, -n без DNS, -v детально)
sudo iptables -F                # Очистити всі існуючі правила (ОБЕРЕЖНО!)
sudo iptables -A INPUT -p tcp --dport 22 -j ACCEPT # Додати (-A) дозвіл на SSH
sudo iptables -A INPUT -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT # Дозволити вже встановлені з'єднання
sudo iptables -A INPUT -j DROP  # В кінці списку додати загальний DROP
```

### Типові помилки та Troubleshooting (Фаєрвол)

- **Lockout (Самоблокування):** Виконання `sudo ufw enable` або правила `DROP` до того, як дозволено порт 22. SSH-сесія обривається, потрібен доступ через консоль провайдера.
    
- **Docker Bypass:** Ти налаштував `ufw deny 8080`, але Docker-контейнер `-p 8080:80` доступний з інтернету! Чому? Docker пише правила в таблицю **NAT**, яка обробляється ядром раніше, ніж таблиця **Filter**, з якою працює UFW. _Вирішення:_ Публікуй порти на локалхост (`-p 127.0.0.1:8080:80`) і використовуй Nginx.
    
- **Пакет не доходить (Timeout):**
    
    1. _Hypothesis 1:_ Правило UFW додано, але стоїть нижче правила DROP (`ufw status numbered`).
        
    2. _Hypothesis 2:_ Трафік блокується на рівні Cloud Provider (AWS Security Group). Локальний фаєрвол і хмарний працюють послідовно.
        
    3. _Hypothesis 3:_ Провайдер блокує вихідні пакети (напр., вихідний порт 25 закритий майже всіма провайдерами).
        

## 4. Базові Утиліти Діагностики (Швейцарський ніж L3/L4)

- **`ip` (Сучасна заміна `ifconfig`):**
    
    - `ip a` (або `ip addr show`): Список усіх інтерфейсів, їхні IPv4/IPv6, MAC та маски (CIDR `/24`).
        
    - `ip r` (або `ip route`): Таблиця маршрутизації. `default via ...` — це адреса шлюзу.
        
- **`ping` (ICMP):** Перевіряє, чи "живий" віддалений вузол. У Linux працює нескінченно. Прапорець `-c N` вказує точну кількість пакетів (`ping -c 4 google.com`).
    
- **`ss` (Мережева статистика):** Аналіз з'єднань і портів. Головна комбінація `-tulnp`:
    
    - `-t` (TCP), `-u` (UDP), `-l` (listening - відкриті порти).
        
    - `-n` (numeric - вивід цифрами без резолвінгу доменів для швидкості).
        
    - `-p` (programs - показує PID і назву процесу, вимагає `sudo`).
        
- **`traceroute` та `tracepath`:** Показує ланцюжок роутерів до цілі. Працює за допомогою маніпуляції полем TTL. `traceroute` використовує UDP (за замовчуванням у Linux). `tracepath` — сучасна альтернатива, що не вимагає прав root і показує MTU.
## 5. **DNS (Domain Name System), /etc/hosts та розпізнавання імен.**



1#DNS — це глобальна ієрархічна розподілена база даних, яка перетворює зрозумілі людині доменні імена (наприклад, `github.com`) на IP-адреси (наприклад, `140.82.113.3`), які використовує мережевий рівень (TCP/IP) для маршрутизації пакетів.

  
#2. Яку проблему вирішує?

3. **Пам'ять:** Людям важко запам'ятовувати IP-адреси (особливо IPv6).
    
      
    
4. **Міграція без болю:** Якщо сервер фізично згорів, ти піднімаєш новий сервер (з новим IP). Без DNS тобі довелося б обдзвонити всіх клієнтів і сказати новий IP. З DNS ти просто змінюєш запис у базі, і клієнти продовжують ходити на `api.company.com`.
    
      
    

Навіщо DevOps це використовує?

- **Service Discovery:** У Kubernetes (через CoreDNS) мікросервіси знаходять один одного за іменами (напр., `backend` звертається до `database`), а не за IP, які постійно змінюються при рестарті контейнерів.
    
      
    
- **Load Balancing (Round Robin):** До одного домену прив'язують кілька IP-адрес. DNS-сервер віддає їх по черзі, розподіляючи навантаження між серверами.
    
      
    
- **Внутрішні зони (Private DNS):** Створення доменів, які існують тільки всередині AWS VPC (напр., `db.internal`), щоб їх не було видно з інтернету.
    
      
    

Як це працює? (Логіка розпізнавання)

Коли ти вводиш `curl [https://example.com](https://example.com)`, операційна система виконує чіткий алгоритм пошуку (DNS Resolution). Він працює до першого збігу:

  

Plaintext

```
[ Запит: example.com ]
      ↓
1. OS Cache (Чи не питали ми це нещодавно?) -> Якщо так, віддаємо IP.
      ↓
2. /etc/hosts (Локальний файл-перевизначення) -> Якщо є запис, беремо його.
      ↓
3. System Resolver (/etc/resolv.conf) -> ОС питає локальний DNS-сервер провайдера.
      ↓
4. Root DNS Servers (.) -> Якщо провайдер не знає, він питає найголовніші сервери світу.
      ↓
5. TLD Servers (.com) -> Кореневий сервер відправляє до серверів, що керують зоною .com.
      ↓
6. Authoritative Server -> Сервер, що керує саме example.com, віддає остаточний IP.
```

Основні поняття (MUST KNOW)

|**Запис / Термін**|**Призначення**|**Приклад / Використання DevOps**|
|---|---|---|
|**A Record**|Мапить домен на IPv4.|`web.site.com -> 192.168.1.10`|
|**CNAME**|Мапить домен на інший домен (Alias).|`[www.site.com](https://www.site.com) -> site.com`. (CNAME не може вказувати на IP).|
|**MX Record**|Вказує на поштові сервери домену.|Маршрутизація email.|
|**NS Record**|Вказує на Authoritative сервери зоні.|Кому AWS Route53 делегує управління доменом.|
|**TXT Record**|Будь-який текст.|Доведення права власності на домен (для отримання SSL або інтеграції з Google Workspace).|
|**TTL** (Time To Live)|Час життя запису в кеші (в секундах).|`TTL 300` — кеш живе 5 хвилин. Довгий TTL = швидше працює, але зміни IP оновлюватимуться у клієнтів довго.|

Команди та конфігурація

Головний інструмент DevOps для роботи з DNS — утиліта `dig` (Domain Information Groper).

  

Bash

```
# 1. Повний запит (покаже час, сервер, який відповів, та всі секції)
dig google.com

# 2. Отримати ТІЛЬКИ IP-адресу (для bash-скриптів)
dig +short google.com

# 3. Запитати конкретний тип запису (наприклад, CNAME або MX)
dig MX google.com

# 4. Запитати конкретний DNS-сервер (в обхід системного /etc/resolv.conf)
dig @8.8.8.8 google.com

# 5. Трасування (пройти весь шлях від Root серверів до Authoritative)
dig +trace google.com
```

Розбір команди: `dig @1.1.1.1 example.com A`

- `dig` — сама утиліта.
    
      
    
- `@1.1.1.1` — (Опціонально) питаємо конкретний сервер (тут це Cloudflare DNS), ігноруючи налаштування нашої ОС.
    
      
    
- `example.com` — домен, який нас цікавить.
    
      
    
- `A` — (Опціонально) тип запису. За замовчуванням `dig` завжди шукає запис типу A.
    
      
    

Реальний сценарій DevOps

Компанія переїжджає на новий сервер.

Старий IP: `10.0.0.1`. Новий IP: `20.0.0.2`.

Девопс зменшує TTL для `api.company.com` з 86400 (24 години) до 60 (1 хвилина) за добу до переїзду. Вночі він змінює в DNS `A`-запис на `20.0.0.2`. Завдяки низькому TTL, через 1 хвилину весь трафік клієнтів автоматично починає йти на новий сервер.

  

Troubleshooting: Як дебажити DNS

**Проблема:** Ти змінив IP-адресу домену в панелі управління, але сайт все одно відкривається зі старого сервера.

**Симптом:** Браузер або `curl` йдуть на стару IP-адресу.

  

**Методика мислення:**

  

1. _Hypothesis 1:_ У системі є жорстке перевизначення.
    
      
    - _Check:_ `cat /etc/hosts`. Якщо там прописаний старий IP — система ніколи не піде в інтернет за новим.
        
          
        
2. _Hypothesis 2:_ DNS-кеш провайдера ще не оновився через високий TTL.
    
      
    - _Check:_ `dig @8.8.8.8 mydomain.com` (питаємо Google) і `dig @1.1.1.1 mydomain.com` (питаємо Cloudflare). Якщо вони повертають різні IP, значить DNS-зона ще в процесі оновлення (Propagation). Треба просто чекати, поки витече TTL старого запису.
        
          
        
3. _Hypothesis 3:_ Впав локальний DNS-резолвер.
    
      
    - _Check:_ `ping 8.8.8.8` працює, а `ping google.com` каже `Temporary failure in name resolution`. Значить, пропав доступ до DNS-сервера, вказаного у `/etc/resolv.conf`.

## 6. Прикладні Утиліти: `nc` та `curl`

### `nc` (Netcat) — Інструмент L4

Вміє читати і писати сирі байти через TCP/UDP без написання коду. Використовується для сканування портів, дебагу та створення фейкових серверів.

- `-l` (Listen): Режим сервера.
    
- `-p` (Port): Вказати локальний порт.
    
- `-v` (Verbose): Детальна інформація.
    
- `-z` (Zero-I/O): Встановити з'єднання і одразу закрити (ідеально для сканування фаєрволів: `nc -vz 10.0.0.5 5432`).
    
- `-u` (UDP): Використовувати UDP.
    
- **`-k` (Keep open):** Змушує `nc` не вмирати після першого з'єднання.
    
    - _DevOps Сценарій (Вічний фейковий сервер):_ `echo "HTTP/1.1 200 OK" | nc -l -k -p 8000`. Можна робити `curl` безліч разів.
        

### `curl` (Client URL) — Інструмент L7

Консольна утиліта для передачі даних HTTP/HTTPS. Створена для скриптів. _Під капотом:_ Розбирає URL → йде в DNS → створює TCP-сокет → ініціює TLS Handshake → формує HTTP-запит → виводить тіло відповіді.

**Анатомія HTTP-запиту:**

- `GET / HTTP/1.1` (Метод, Шлях, Версія протоколу).
    
- `Host:` Найважливіший заголовок для веб-серверів (Nginx), щоб розуміти, контент якого саме сайту віддати (Virtual Hosts).
    
- `User-Agent:` Ідентифікатор клієнта.
    
- `Accept: */*` Які формати приймає клієнт.
    

**Прапорці та Сценарії `curl`:**

- **`-v` (Verbose):** Показує DNS, TCP, TLS та заголовки. Найголовніший інструмент дебагу (зокрема SSL-сертифікатів: ким виданий, коли прострочиться).
    
- **`-I` (Head):** Запитує ТІЛЬКИ заголовки. Ідеально для дебагу Nginx (якщо `502` — бекенд впав, якщо `403` — проблема з правами).
    
- `-L` (Location): Автоматично переходити за редіректами.
    
- `-X` / `-d` / `-H`: Зміна методу, відправка payload та додавання кастомних заголовків. `curl -X POST http://api/health -H "Content-Type: application/json" -d '{"check": true}'`
    
- `-O`: Зберегти файл на диск.
    

**Як змусити curl віддати ТІЛЬКИ статус-код:** `curl -s -o /dev/null -w "%{http_code}" [https://example.com](https://example.com)`

- `-s` (silent) — вимикає шкалу завантаження.
    
- `-o /dev/null` — скидає HTML-код у чорну діру.
    
- `-w "%{http_code}"` — друкує виключно змінну статусу (напр. 200).
