
### 1. Бізнес-контекст: Навіщо це потрібно?

Уяви, що ти розгорнув вебсервер (наприклад, Nginx) і підключив до нього базу даних. Якщо ти запустиш Nginx від імені адміністратора (`root`), і хакер знайде вразливість у вебсайті, він автоматично отримає повний контроль над усім сервером і зможе видалити базу даних.

Щоб цього не сталося, DevOps-інженери використовують **Принцип найменших привілеїв (Principle of Least Privilege)**. Nginx має працювати від імені спеціального, максимально "обмеженого" користувача, який має право читати лише файли самого вебсайту і більше нічого.

Команди для управління користувачами та правами — це твій інструмент для побудови таких невидимих стін між процесами та даними на сервері.

### 2. Анатомія та Архітектура (Як Linux бачить користувачів і права)

Для нас користувач — це ім'я (наприклад, `ubuntu` або `nginx`). Але ядро Linux, як ми вже знаємо, не розуміє тексту. Воно розуміє лише цифри.

**Анатомія користувача:**

* **UID (User ID):** Унікальний номер користувача (Root завжди має `UID=0`).
* **GID (Group ID):** Унікальний номер основної групи користувача.
* Вся інформація про користувачів лежить у простому текстовому файлі: `/etc/passwd`.
* Хеші паролів (щоб їх ніхто не міг прочитати) сховані в іншому файлі, доступному лише для root: `/etc/shadow`.

**Анатомія прав доступу (Inodes):**
У Linux кожен файл і папка належать одному **Користувачу (Owner)** та одній **Групі (Group)**.
Права діляться на три категорії (UGO) і три дії (RWX):

```text
Категорії:
U (User)  — Власник файлу
G (Group) — Група, якій належить файл
O (Other) — Усі інші користувачі в системі (світ)

Дії:
r (Read)    — Читання (цифрове значення: 4)
w (Write)   — Запис/редагування (цифрове значення: 2)
x (Execute) — Виконання програми або вхід у директорію (цифрове значення: 1)

```

Коли ти робиш `ls -l`, ти бачиш рядок на кшталт: `-rwxr-xr--`.

* Перший символ `-` означає, що це файл (якщо `d` — директорія).
* Наступні три `rwx` (4+2+1 = **7**) — власник може читати, писати і запускати.
* Наступні три `r-x` (4+0+1 = **5**) — група може лише читати і запускати.
* Останні три `r--` (4+0+0 = **4**) — усі інші можуть лише читати.
Тобто `rwxr-xr--` — це цифри **754**.

### 3. Еволюція складності (Практичні команди)

**Рівень 1: Базове управління (Створення та зміна власника)**

```bash
# Створити нового користувача з іменем developer
sudo useradd developer

# Задати йому пароль (система попросить ввести його двічі)
sudo passwd developer

# Змінити власника файлу (CHange OWNer) з поточного на developer
sudo chown developer config.txt

```

**Рівень 2: Групи та Права (Спільна робота)**

```bash
# Додати користувача developer до існуючої групи docker
# ВАЖЛИВО: Завжди використовуй -aG (append Group). 
sudo usermod -aG docker developer

# Змінити групу, якій належить файл (CHange GRouP)
sudo chgrp developers_team project_folder/

# Змінити права (CHange MODe). Наприклад, дати власнику всі права (7), 
# групі - читання і виконання (5), іншим - нічого (0).
chmod 750 script.sh

```

**Рівень 3: Production (Системні користувачі)**
Коли ми встановлюємо базу даних або вебсервер, ми не створюємо звичайного користувача. Ми створюємо "системного" користувача, під яким фізично неможливо зайти в термінал. Це робиться для максимальної безпеки.

```bash
# -r (system user), -s /usr/sbin/nologin (заборонити вхід у термінал)
sudo useradd -r -s /usr/sbin/nologin prometheus_user

# Рекурсивно (-R) змінити власника і групу одночасно
sudo chown -R prometheus_user:prometheus_group /var/lib/prometheus/

```

### 4. Типові помилки (Анти-патерни)

1. **Гріх "chmod 777"**: Найчастіша помилка новачків. Якщо скрипт або застосунок вибиває помилку "Permission denied", недосвідчений розробник просто пише `chmod 777 файл` (дозволити всім читати, писати і виконувати). Це величезна діра в безпеці. DevOps повинен розібратися, якому саме користувачу не вистачає прав, і видати мінімально необхідні (наприклад, через `chown` або групи).
2. **Забутий прапорець `-a` в `usermod**`: Якщо ти напишеш `usermod -G docker developer` (без `a`), система видалить** користувача з усіх інших груп, у яких він був, і залишить ТІЛЬКИ в групі `docker`. Якщо це був твій користувач, ти можеш втратити права `sudo` і заблокувати собі доступ до сервера. Завжди використовуй `usermod -aG`!
3. **Плутанина з правом Execute (`x`) на директоріях**: Для файлів `x` означає право на запуск (як програму). Але для папок (директорій) `x` означає **право увійти в неї** (через команду `cd`). Якщо ти даси папці права `r--` (читання без виконання), користувач побачить файли всередині через `ls`, але не зможе ні перейти в папку, ні прочитати самі файли.

### 5. Тренувальна співбесіда

**Junior:** Як дати звичайному файлу права на виконання, не використовуючи цифри (наприклад, 755)?

* *Сильна відповідь:* Я використаю символьний синтаксис команди `chmod`, а саме: `chmod +x filename`. Це додасть право на виконання (execute) для власника, групи та всіх інших, не змінюючи при цьому поточні права на читання чи запис.

**Middle:** Що таке `/etc/passwd` і `/etc/shadow`? Чому ці дані розділені на два файли?

* *Сильна відповідь:* `/etc/passwd` містить публічну інформацію про користувачів (UID, домашня директорія, оболонка) і він доступний для читання всім процесам у системі, оскільки багатьом програмам треба перетворювати UID на імена. Файл `/etc/shadow` зберігає хеші паролів. Він доступний лише для `root`, щоб захистити паролі від брутфорсу (перебору) звичайними користувачами.

**Senior:** Уяви ситуацію: Користувач `alice` належить до групи `devs`. Файл `secret.txt` належить користувачу `bob` і групі `devs`. Права на файл встановлено як `---rwx---` (070). Чи зможе `alice` прочитати цей файл?

* *Сильна відповідь:* Так, зможе. Ядро Linux перевіряє права в суворому порядку: Власник -> Група -> Інші. Спочатку воно бачить, що `alice` не є власником (`bob`). Потім воно перевіряє групу. Оскільки `alice` є в групі `devs`, застосовуються права групи (`rwx`). Права власника (`---`) ігноруються.
