# 📖 Повний розбір модуля `requests`

## 1. Основи HTTP-протоколу в `requests`

Кожен HTTP-запит має **метод** (що ми робимо) та повертає **відповідь (Response)**.

  

Python

```
import requests

# Звичайний GET-запит
response = requests.get("https://api.github.com")

print(response.status_code)  # Наприклад: 200
```

## 2. Основні HTTP-методи

|**Метод**|**Мета у DevOps/API**|**Як викликати в requests**|
|---|---|---|
|**GET**|Отримати дані (прочитати конфіг, список контейнерів)|`requests.get(url)`|
|**POST**|Створити новий ресурс (відправити алерт, створити тикет)|`requests.post(url, json=data)`|
|**PUT / PATCH**|Оновити існуючий ресурс (змінити конфігурацію)|`requests.put(url, json=data)`|
|**DELETE**|Видалити ресурс (видалити старий образ або под)|`requests.delete(url)`|

## 3. Анатомія об'єкта Відповіді (`Response`)

Коли ти робиш запит, `requests` повертає об'єкт `Response`, з якого можна витягнути геть усе:

  

Python

```
import requests

response = requests.get("https://jsonplaceholder.typicode.com/posts/1")

# 1. Статус-код (200 - OK, 404 - Not Found, 500 - Server Error)
print(response.status_code)

# 2. Перевірка на успішність (True, якщо статус від 200 до 399)
print(response.ok)

# 3. Текст відповіді (RAW HTML / plain text)
print(response.text)

# 4. Автоматичне перетворення JSON у Python-словник (КРИТИЧНО ВАЖЛИВО!)
data = response.json()
print(data["title"])  # Працюємо як зі звичайним dict!

# 5. Заголовки (Headers) від сервера
print(response.headers["Content-Type"])
```

## 4. Передача параметрів та даних у запитах

### А. Параметри в URL (Query Parameters) для GET-запитів

Замість того, щоб формувати URL вручну вида `[https://site.com/search?q=python&page=1](https://site.com/search?q=python&page=1)`, використовуй параметр `params`:

  

Python

```
import requests

params = {
    "q": "python",
    "page": 1,
    "sort": "desc"
}

# Сформує URL: https://httpbin.org/get?q=python&page=1&sort=desc
response = requests.get("https://httpbin.org/get", params=params)
```

### Б. Передача JSON-даних у POST-запитах

Для API найчастіше передаються JSON-структури:

  

Python

```
import requests

payload = {
    "title": "Alert: High CPU Usage",
    "server": "web-01",
    "severity": "critical"
}

# Параметр json= сам перетворить словник на JSON і додасть заголовок Content-Type: application/json
response = requests.post("https://httpbin.org/post", json=payload)
```

### В. Заголовки (Headers) та Токени авторизації

Для передачі API-ключів, токенів або `User-Agent`:

  

Python

```
import requests

headers = {
    "Authorization": "Bearer YOUR_SECRET_TOKEN_HERE",
    "User-Agent": "MyDevOpsScript/1.0"
}

response = requests.get("https://api.github.com/user", headers=headers)
```

## 5. Обробка помилок та Таймаути (Best Practices)

У реальному мережевому середовищі сервери можуть бути недоступні, скидати з'єднання або відповідати занадто довго.

  

### ⚠️ Золоті правила роботи з `requests`:

1. **ЗАВЖДИ вказуй `timeout`:** Без нього скрипт може зависнути НАЗАВЖДИ, чекаючи на відповідь!
    
      
    
2. **Використовуй `.raise_for_status()`:** Викидає виняток, якщо статус-код відповіді показує помилку (4xx або 5xx).
    
      
    
3. **Обгортай у `try / except`:**
    
      
    

Python

```
import requests

url = "https://api.github.com/users/octocat"

try:
    # Таймаут: 3 секунди на підключення, 5 секунд на отримання даних
    response = requests.get(url, timeout=(3, 5))
    
    # Якщо зафіксовано статус 4xx або 5xx — буде викликано HTTPError
    response.raise_for_status()
    
    data = response.json()
    print(f"Користувач: {data['name']}")

except requests.exceptions.Timeout:
    print("⏳ Помилка: Сервер не відповів за відведений час (Timeout)!")
except requests.exceptions.HTTPError as err:
    print(f"❌ Помилка HTTP: {err} (Статус: {response.status_code})")
except requests.exceptions.RequestException as err:
    print(f"🚨 Критична мережева помилка: {err}")
```

## 6. Сесії (`requests.Session`)

Якщо потрібно зробити **багато запитів до одного і того ж сервера**, використовуй `requests.Session()`.

  

**Переваги:**

  

- Зберігає куки (cookies) та заголовки між запитами.
    
      
    
- Прискорює виконання, оскільки повторно використовує те саме TCP-з'єднання (Keep-Alive).
    
      
    

Python

```
import requests

# Створюємо сесію
session = requests.Session()
session.headers.update({"Authorization": "Bearer MY_TOKEN"})

# Усі наступні запити автоматично містять заголовок Authorization!
r1 = session.get("https://httpbin.org/headers")
r2 = session.get("https://httpbin.org/user-agent")
```

### Дерево помилок

У бібліотеці `requests` дуже багато різних помилок:

- `Timeout` (чекали занадто довго)
    
- `ConnectionError` (немає інтернету або домену не існує)
    
- `TooManyRedirects` (сайт нескінченно перенаправляє запит)
    

Щоб нам не довелося писати 10 різних блоків `except` для кожної з них, розробники бібліотеки створили "батьківську" (універсальну) помилку. Вона називається **`requests.exceptions.RequestException`**.

Якщо ти напишеш `except requests.exceptions.RequestException:`, ти кажеш інтерпретатору: _"Якщо станеться БУДЬ-ЯКА мережева помилка під час запиту — лови її тут"_.

  
# 1. HTTP Статус-коди (Status Codes)

Статус-код складається з 3 цифр. **Перша цифра** визначає категорію (групу) відповіді:

  

### 🟢 **2xx — Success (Успіх)**

Запит отримано, зрозуміло і успішно оброблено сервером.

  

- **`200 OK`** — стандартна успішна відповідь на більшість запитів (GET, PUT, PATCH).
    
      
    
- **`201 Created`** — запит виконано успішно, і в результаті було створено новий ресурс (найчастіше на POST-запит).
    
      
    
- **`204 No Content`** — запит виконано успішно, але сервер навмисно не повертає ніякого тіла відповіді (часто при DELETE).
    
      
    

### 🟡 **3xx — Redirection (Перенаправлення)**

Клієнту потрібно зробити додаткові дії для отримання ресурсу (перейти на іншу адресу).

  

- **`301 Moved Permanently`** — ресурс назавжди переміщено на новий URL. Браузери та пошуковики запам'ятовують це і надалі звертаються за новою адресою.
    
      
    
- **`302 Found` (Moved Temporarily)** — ресурс тимчасово знаходиться за іншою адресою.
    
      
    
- **`304 Not Modified`** — ресурс не змінювався з моменту останнього запиту. Використовується для кешування (економить трафік).
    
      
    

### 🟠 **4xx — Client Errors (Помилки Клієнта)**

Проблема на боці **клієнта**: передано неправильні дані, відсутні права доступу або запитано неіснуючу сторінку.

  

- **`400 Bad Request`** — сервер не зміг зрозуміти запит через синтаксичну помилку в даних (наприклад, кривий JSON).
    
      
    
- **`401 Unauthorized`** — відсутня або невірна автентифікація (не передано API-ключ, токен або пароль).
    
      
    
- **`403 Forbidden`** — клієнт автентифікований, але у нього **немає прав** доступу до цього ресурсу (наприклад, звичайний юзер намагається викликами адмінку).
    
      
    
- **`404 Not Found`** — запитуваний ресурс не знайдено на сервері.
    
      
    
- **`409 Conflict`** — конфлікт у стані ресурсу (наприклад, спроба створити користувача з email, який вже існує в базі).
    
      
    

### 🔴 **5xx — Server Errors (Помилки Сервера)**

Клієнт відправив правильний запит, але упав або застряг сам **сервер**.

  

- **`500 Internal Server Error`** — універсальна помилка: щось зламалося в коді бекенду (uncaught exception, упала база даних тощо).
    
      
    
- **`502 Bad Gateway`** — сервер-проксі (наприклад, Nginx) отримав недійсну відповідь від внутрішнього сервісу (наприклад, Gunicorn/Gunicorn/Node.js упав).
    
      
    
- **`503 Service Unavailable`** — сервер тимчасово не може обробляти запити (перевантажений або знаходиться на технічному обслуговуванні).
    
      
    
- **`504 Gateway Timeout`** — сервер-проксі не дочекався відповіді від внутрішнього сервісу за відведений час.
    
      

"Група 4xx — це завжди помилка на боці клієнта. Тобто мій скрипт сформував неправильний запит. Наприклад, статус 403 означає, що запит дійшов до сервера, але сервер відмовив в обробці через брак прав доступу (неправильний або відсутній API-ключ).

Група 5xx — це проблема на боці самого сервера. Клієнт зробив усе правильно, але сервер не зміг обробити запит. Зокрема, 502 Bad Gateway зазвичай означає, що наш балансувальник або веб-сервер (як-от Nginx) не зміг отримати відповідь від upstream-сервера (наприклад, Docker-контейнера з нашим додатком), тому що той перезавантажується або завис."

# 2. Базові HTTP-методи (HTTP Methods / Verbs)

Метод вказує на **дію**, яку ми хочемо виконати над ресурсом за вказаним URL.

  

### 1. **`GET`** — Отримати дані

- **Призначення:** Читання ресурсу (наприклад, завантажити список користувачів або конфіг).
    
      
    
- **Особливості:** Не повинен змінювати стан на сервері (ідемпотентний та безпечний). Передає параметри прямо у строці URL (наприклад, `/users?page=2`).
    
      
    

### 2. **`POST`** — Створити новий ресурс

- **Призначення:** Відправка даних на сервер для створення нового об'єкта (новий тикет, новий користувач, відправка форми).
    
      
    
- **Особливості:** Дані передаються у **тілі запиту (body)** у форматі JSON, XML або Form-Data. **Не ідемпотентний** (два однакових POST-запити створять два різних записи в БД).
    
      
    

### 3. **`PUT`** — Замінити ресурс повністю

- **Призначення:** Оновлення існуючого ресурсу. Якщо об'єкт існує — він повністю перезаписується новими даними. Якщо його немає — створюється новий.
    
      
    
- **Особливості:** **Ідемпотентний** (скільки б разів поспіль ти не відправив один і той самий PUT-запит, підсумковий стан об'єкта на сервері буде однаковим).
    
      
    

### 4. **`PATCH`** — Частково змінити ресурс

- **Призначення:** Точкове оновлення. Передаються тільки ті поля, які треба змінити (наприклад, змінити тільки email користувача, не чіпаючи ім'я та аватар).
    
      
    

### 5. **`DELETE`** — Видалити ресурс

- **Призначення:** Видалення вказаного об'єкта за його URL (наприклад, `DELETE /users/42`).
    
      
    
- **Особливості:** **Ідемпотентний** (перший виклик видалить об'єкт, повторні виклики повертатимуть 404 або 204, але стан системи більше не зміниться).
    
      
    

### 💡 Що таке "Ідемпотентність"?

Метод є **ідемпотентним**, якщо повторне виконання одного й того ж запиту безліч разів дає той самий результат на сервері, що й один виклик.

  

- `GET`, `PUT`, `DELETE` — **ідемпотентні**.
    
      
    
- `POST` — **НЕ ідемпотентний** (повторний виклик повторно виконає дію, наприклад створить дублікат).
