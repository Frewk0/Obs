## 1. MENTAL MODEL & INTERNAL MECHANICS 🟥 MUST KNOW

### 1.1. WHAT (Що це таке)

Контейнери створені для ізоляції. За замовчуванням контейнер має власний, повністю відокремлений мережевий стек завдяки механізму **Network Namespace** (ізоляція на рівні ядра Linux). У нього своя віртуальна мережева карта (`eth0`), свій IP-адрес і власна таблиця маршрутизації (Routing table).

  

### 1.2. INTERNAL MECHANICS (Як вони спілкуються) 🟪 ADVANCED

Як з'єднати ізольований контейнер з інтернетом або іншим контейнером? Docker використовує базові примітиви Linux:

  

1. **Virtual Bridge (`docker0`):** При встановленні Docker створює віртуальний комутатор (switch) на хост-системі.
    
      
    
2. **veth pair (Virtual Ethernet):** Для кожного контейнера Docker створює віртуальний кабель із двох кінців. Один кінець вставляється в Network Namespace контейнера (і стає там `eth0`), а інший кінець — у bridge `docker0` на хості.
    
      
    
3. **NAT (Network Address Translation):** Оскільки IP-адреси контейнерів (наприклад, `172.17.0.2`) є сірими (приватними), Docker налаштовує правила `iptables` на хості, щоб випускати трафік з контейнера в інтернет через IP хоста (Masquerading).
    
      
    

## 2. NETWORK DRIVERS (Мережеві драйвери) 🟥 MUST KNOW

Docker абстрагує складність Linux Networking через драйвери.

  

|**Driver**|**Mechanics & Behavior**|**Typical Use Case**|
|---|---|---|
|**`bridge`**|**Default.** Створює віртуальний комутатор. Контейнери в одній bridge-мережі бачать один одного.|Звичайні застосунки, мікросервіси, бази даних.|
|**`host`**|Знімає Network Namespace. Контейнер використовує мережу хоста. Якщо Nginx в контейнері слухає порт 80, це фізичний порт 80 твого сервера.|Високонавантажені системи, де NAT створює зайвий overhead (затримку).|
|**`none`**|Повна ізоляція. У контейнера є тільки `lo` (localhost `127.0.0.1`).|Batch processing, робота з криптографією.|
|**`macvlan`**|🟪 Призначає контейнеру реальну MAC-адресу. Він виглядає як фізичний пристрій у твоїй домашній/офісній мережі (в обхід NAT).|Legacy застосунки, які вимагають прямого доступу до Layer 2 мережі.|

## 3. SERVICE DISCOVERY (Вбудований DNS) 🟨 SHOULD KNOW

### 3.1. The Problem

IP-адреси контейнерів є динамічними (Dynamic). Якщо контейнер з базою даних перезапуститься, він може отримати інший IP. Хардкодити (hardcode) IP-адреси в конфігах бекенду — це грубий Anti-pattern.

  

### 3.2. The Solution: Embedded DNS

Docker має власний DNS-сервер (Embedded DNS), який працює всередині кожного контейнера за адресою `127.0.0.11`.

  

- _Internal Mechanics:_ Коли контейнер стартує, Docker автоматично реєструє його ім'я (`--name db`) та його поточний IP у своєму внутрішньому DNS.
    
      
    
- Коли твій бекенд робить `ping db`, запит йде на `127.0.0.11`, і той повертає актуальний IP.
    
      
    

### 3.3. КРИТИЧНИЙ НЮАНС (The Default Bridge Trap) 🔴

Вбудований DNS **НЕ ПРАЦЮЄ** у стандартній мережі (Default `bridge`), яка використовується, якщо ти не вказав прапорець `--network`.

  

- _Best Practice:_ **Завжди** створюй власну (user-defined) мережу для своїх застосунків. Тільки там працює автоматичне вирішення імен (Service Discovery).
    
      
    

## 4. PORT PUBLISHING (`-p` vs `EXPOSE`) 🟥 MUST KNOW

### 4.1. `EXPOSE` (Dockerfile)

- Це просто метадані (Documentation).
    
      
    
- Команда `EXPOSE 80` **нічого не робить** з точки зору мережі. Вона лише підказує розробнику: "Цей застосунок слухає 80-й порт".
    
      
    

### 4.2. Прапорець `-p` / `--publish` (CLI)

Синтаксис: `-p <HOST_PORT>:<CONTAINER_PORT>` (або `IP:HOST_PORT:CONTAINER_PORT`).

  

_Internal Mechanics:_ Docker звертається до ядра Linux і створює правило **DNAT** (Destination NAT) у ланцюжку `PREROUTING` таблиці `iptables`.

  

**Security Trade-offs & Examples:**

  

- `docker run -p 8080:80 nginx`
    
      
    - _Behavior:_ Публікує на `0.0.0.0:8080`. Будь-хто з інтернету може зайти на цей порт.
        
          
        
- `docker run -p 127.0.0.1:8080:80 nginx`
    
      
    - _Behavior (Best Practice для локальних БД):_ Публікує тільки на localhost твого сервера. З інтернету доступу не буде. Безпечно для Redis або PostgreSQL, якщо до них підключаються тільки локальні процеси хоста.


## 6. PRODUCTION EDGE CASES & TROUBLESHOOTING 🟪 ADVANCED

### 6.1. The UFW Bypass (Пастка безпеки) 🔴

- **Problem:** Ти налаштував фаєрвол UFW: `sudo ufw default deny incoming`. Сервер захищений. Ти запускаєш `docker run -p 3306:3306 mysql`. Ти очікуєш, що порт 3306 закритий фаєрволом. Але хакери зламують твою БД.
    
      
    
- **Internal Mechanics:** Docker працює напряму з `iptables`, додаючи свої правила у ланцюжок `DOCKER`, який обробляється **ДО** правил UFW. Docker пробиває фаєрвол наскрізь.
    
      
    
- **Fix:** Якщо не хочеш пускати інтернет, роби publish тільки на локалхост: `-p 127.0.0.1:3306:3306`. (Існують способи інтеграції UFW і Docker, але вони вимагають складної маніпуляції з конфігами).
    
      
    

### 6.2. "Connection Refused" зсередини контейнера 🟥 MUST KNOW

Це помилка №1 серед Junior-розробників.

  

- **Symptom:** Ти написав Python бекенд. Він стартує і каже: `Running on [http://127.0.0.1:8000](http://127.0.0.1:8000)`. Ти робиш `docker run -p 8000:8000 my-api`. Заходиш у браузер — `Connection Refused` або `Page Not Found`.
    
      
    
- **Investigation:** Порти прокинуті правильно (`-p 8000:8000`). Але застосунок всередині слухає `127.0.0.1` (localhost **контейнера**).
    
      
    
- **Root Cause:** `127.0.0.1` для процесу в контейнері — це сам контейнер (його власний Network Namespace). Трафік з хоста (DNAT) приходить на інтерфейс `eth0` контейнера, а застосунок слухає тільки `lo`.
    
      
    
- **The Fix:** Застосунок (Python/Node/Java) у контейнері **ЗАВЖДИ має бути налаштований на прослуховування `0.0.0.0`** (всі інтерфейси). Тільки тоді він зможе приймати зовнішній трафік.
    
      
    

### 6.3. Overlapping Subnets (Конфлікт підмереж)

- **Problem:** Якщо твоя корпоративна мережа в офісі використовує адреси `172.17.X.X` або `172.18.X.X`, і Docker створює bridge-мережу з такими ж IP, VPN або офісна мережа відпаде. Ядро Linux не знатиме, куди слати пакети (бо є два однакові маршрути).
    
      
    
- **Fix:** Вказати інший діапазон у `daemon.json` (`"bip": "10.200.0.1/24"`) або при створенні мережі: `docker network create --subnet=10.0.0.0/24 my-net`.
    
      
    

## 7. MEMORY CORE

**Що я повинен пам'ятати без підглядання:**

  

- Default `bridge` не має вбудованого DNS. Завжди роби `docker network create`.
    
      
    
- `-p 8080:80` = HOST:CONTAINER. Відкриває порт для всього світу, ігноруючи UFW.
    
      
    
- `-p 127.0.0.1:8080:80` = Безпечний доступ тільки з хоста.
    
      
    
- Застосунок всередині контейнера завжди має слухати `0.0.0.0`, а не `127.0.0.1`.
    
      
    
- `EXPOSE` у Dockerfile нічого не робить фізично. Це просто документація.
