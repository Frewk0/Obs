### Анатомія локального репозиторію

Щоб працювати з Git, потрібні лише чотири базові команди, які покривають 80% щоденної рутини:

1. `git init` — перетворює звичайну папку на систему контролю версій. Вона створює приховану папку `.git`, де Git зберігає всю свою магію та історію.
    
2. `git status` — твій "радар". Цю команду ти будеш використовувати постійно. Вона показує поточний стан: які файли змінені, які додані, а які Git ще взагалі не бачить (Untracked).
    
3. `git add <назва_файлу>` — переміщує файл із робочої директорії (Working Directory) у зону очікування (Staging Area). Ти ніби кажеш: _"Підготуй цей файл до збереження"_.
    
4. `git commit -m "Твоє повідомлення"` — фіксує всі файли із зони очікування в історію. Прапорець `-m` (message) дозволяє одразу написати коментар. Коментарі мають бути чіткими, щоб через рік ти зрозумів, що саме змінив.

### Архітектурна довідка: Механізм ігнорування в Git

У системі Git немає спеціальної команди на кшталт `git ignore <файл>`. Замість цього використовується декларативний підхід через конфігураційний файл.

Щоб Git перестав відстежувати певне сміття, інженер повинен:

1. Створити в корені репозиторію спеціальний прихований текстовий файл. Його назва має бути точно **`.gitignore`** (крапка на початку обов'язкова).
    
2. Усередині цього файлу звичайним текстом прописати правила — назви конкретних файлів, папок або регулярні вирази.
    
3. Наприклад, якщо інженер хоче, щоб Git назавжди "осліп" до всіх текстових файлів, він просто записує у цей файл рядок `*.txt`. Символ зірочки `*` працює як універсальний джокер (wildcard).

# ТЕОРИТИЧНА БАЗА: Концепція "Паралельних світів"

### Навіщо це потрібно в DevOps?

Уяви, що в компанії працює 5 DevOps-інженерів. У вас є один головний скрипт `deploy_prod.sh`, який щодня автоматично оновлює банківську систему.

Тобі дали задачу: _додати в цей скрипт відправку смс-повідомлень про помилки_.

Якщо ти почнеш писати код прямо в робочому файлі `deploy_prod.sh`, а в цей момент інший інженер запустить деплой — **банк ляже**, бо твій код ще дописаний лише наполовину і містить синтаксичні помилки.

**Рішення:** Ти створюєш **гілку** (Branch).

Гілка — це твоя особиста, повністю ізольована пісочниця. Ти береш точну копію `deploy_prod.sh` станом на сьогоднішній ранок, йдеш у свій "паралельний вимір", ламаєш там усе, тестуєш, переписуєш хоч 100 разів. Основна система в цей час продовжує спокійно працювати на старій, стабільній версії. Коли твій код ідеально вилизаний, ти робиш **Злиття** (Merge) — вклеюєш свій новий шматок коду в головний файл.

### Що таке гілка "під капотом" Linux? (Питання рівня Middle)

Новачки думають, що коли ти створюєш гілку, Git бере і фізично копіює всі 100500 файлів проєкту в нову приховану папку. **Ні.** Це б займало гігабайти місця.

Під капотом Git — це геніально проста штука. **Гілка в Git — це просто маленький текстовий файл розміром 41 байт**, всередині якого записаний хеш (номер) одного-єдиного коміту.

Коли ти створюєш гілку, Git просто бере стікер, пише на ньому назву `feature-db` і клеїть його на той самий коміт, на якому ти зараз стоїш.

Plaintext

```
       ( HEAD -> master )
               │
               ▼
[ Коміт А ] ──► [ Коміт B ] ──► [ Коміт C ]  <-- ( Стікер "feature-db" приклеївся сюди )
```

У Git є ще один надважливий вказівник — **`HEAD`**.

`HEAD` — це "курсор". Це те, куди зараз дивляться твої очі. Якщо `HEAD` вказує на `master` — твій текстовий редактор показує файли гілки master. Якщо ти перемикаєш `HEAD` на `feature-db` — вміст папки на твоєму екрані миттєво підміняється ядром Git.

# СЛОВНИК ТЕРМІНІВ (Вчити як Отче наш)

- **`master` (або `main`)** — Головна гілка життя. Священна земля. Там завжди лежить тільки той код, який прямо зараз працює на серверах у клієнтів. Комітити туди напряму — смертний гріх.
    
- **`feature-branch`** — Тимчасова гілка, створена для виконання однієї конкретної задачі (наприклад: `feature-add-database` або `bugfix-login-error`). Задача виконана -> гілка злита в master -> гілка видалена.
    
- **`Checkout` / `Switch`** — Процес переміщення "курсора" (`HEAD`) з однієї гілки на іншу.
    
- **`Merge` (Злиття)** — Операція об'єднання двох історій в одну.
    
- **`Fast-forward merge`** (Швидке перемотування) — Найпростіший вид злиття. Це коли в `master` з моменту твого відходу ніхто нічого не писав. Git просто бере стікер `master` і "пересуває" його вперед по прямій лінії до твого останнього коміту.
    

# АНАТОМІЯ КОМАНД (Покроковий розбір)

### 1. Перегляд існуючих гілок

Bash

```
git branch
```

- **Що робить:** Виводить список усіх стікерів-гілок у цьому репозиторії.
    
- **Параметр `-a`** (`git branch -a`): Покаже взагалі всі гілки, включаючи ті, що лежать десь далеко на серверах GitHub.
    
- **Як читати вивід:** Та гілка, біля якої стоїть зірочка `*` і яка світиться зеленим — це та, **на якій ти стоїш прямо зараз** (куди вказує `HEAD`).
    

### 2. Створення нової гілки

Bash

```
git branch feature-login
```

- **Що робить:** Створює новий стікер `feature-login` і вішає його на поточний коміт.
    
- **Підводний камінь для новачків:** Команда _створює_ гілку, але **НЕ переходить** на неї! Твій `HEAD` залишився стояти на `master`. Ти все ще в старій кімнаті, просто в сусідній з'явилися двері.
    

### 3. Перехід на гілку (Зміна виміру)

Bash

```
git checkout feature-login
# або новіша версія команди:
git switch feature-login
```

- **Що робить:** Бере вказівник `HEAD` і переставляє його на стікер `feature-login`. Файли у твоїй робочій папці миттєво оновлюються до стану цієї гілки.
    

> **ПРОФЕСІЙНИЙ ЛАЙФХАК (Використовують 99% DevOps):**
> 
> Щоб не писати дві окремі команди (створи -> перейди), інженери роблять це в один клік:
> 
> Bash
> 
> ```
> git checkout -b feature-login
> ```
> 
> Прапорець `-b` означає: _"Створи гілку feature-login І ОДРАЗУ ж перестрибни на неї"_.

### 4. Злиття гілок (The Merge)

**ЗОЛОТЕ ПРАВИЛО MERGE, НА ЯКОМУ СИПЛЯТЬСЯ ВСІ ДЖУНИ:**

> _Ти повинен стояти в тій кімнаті, КУДИ ти хочеш занести нові меблі._

Якщо ти написав крутий код у гілці `feature-db`, і хочеш, щоб він з'явився в `master`, твої дії строго такі:

1. КРОК 1: Переходимо додому (в `master`):
    
    Bash
    
    ```
    git checkout master
    ```
    
2. КРОК 2: Затягуємо в себе сусідню гілку:
    
    Bash
    
    ```
    git merge feature-db
    ```
    

- **Що відбувається під капотом:** Git бере коміти з `feature-db`, порівнює їх з `master`, і створює новий об'єднаний стан коду.
    

### 5. Прибирання за собою (Видалення гілки)

Bash

```
git branch -d feature-db
```

- **Що робить:** Зриває і викидає стікер `feature-db`.
    
- **Чому це безпечно:** Самі написані тобою коміти нікуди не зникнуть, вони вже вшиті в історію `master`. Ми просто прибираємо зайву назву з радара, щоб не захаращувати проєкт.
    
- **Прапорець `-D` (велика D):** Це "примусове вбивство". Якщо ти написав в гілці повну дурницю, передумав її зливати в master і хочеш стерти цей паралельний світ назавжди — пиши `git branch -D назва`.

Завдання: Безпечно розширити конфіг проєкту.

Bash

```
# 1. Створюємо робочу гілку під задачу і переходимо туди
git checkout -b feature-add-port

# 2. Робимо нашу інженерну роботу
echo "port: 8080" >> app_config.yml

# 3. Фіксуємо результат в гілці feature-add-port
git add app_config.yml
git commit -m "Add port configuration to config"

# 4. Повертаємося на стабільний master
git checkout master

# 5. Вливаємо перевірену фічу в master
git merge feature-add-port
# Вивід системи: Fast-forward (Швидке перемотування. Все пройшло ідеально)

# 6. Знищуємо відпрацьовану гілку
git branch -d feature-add-port
```

# ТИПОВІ ПОМИЛКИ НОВАЧКІВ ТА ЇХ ДЕБАГ

#### Помилка 1: Спроба перейти на іншу гілку з незбереженими файлами

- **Сценарій:** Ти сидів в `master`, щось правив у конфігу, забув зробити `commit` і пишеш `git checkout feature-1`.
    
- **Вивід Git:** `error: Your local changes to the following files would be overwritten by checkout... Please commit your changes or stash them.`
    
- **Що каже Git:** _"Гей, у тебе на столі розкидані незакінчені креслення! Якщо я зараз перемкну кімнату, вони зімнуться і зникнуть"_.
    
- **Лікування (2 варіанти):**
    
    1. Або закоміть те, що почав (`git commit -m "wip"`).
        
    2. Або використай команду-пилосос **`git stash`** (вона згрібає незакінчену роботу в тимчасовий прихований ящик і робить стіл чистим).
        

#### Помилка 2: "Заблукав у трьох соснах"

- **Сценарій:** Ти створив 8 гілок, пострибав між ними і вже не розумієш, де чий код і хто в кого влитий.
    
- **Команда-рентген для DevOps:**
    
    Bash
    
    ```
    git log --oneline --graph --all
    ```
    
    Вона малює прямо в терміналі кольорову ASCII-схему: гілочки, точечки, хто куди відгалузився і де зараз висить `HEAD`.
