
# ТЕОРИТИЧНА БАЗА: Концепція "Single Source of Truth"

### Навіщо це потрібно в реальних компаніях?

У DevOps діє залізне правило: **Код на твоєму ноутбуці тобі не належить**. Він належить компанії.

Уяви production-команду:

1. Інженер Вася у Варшаві пише конфіг для базу даних.
    
2. Інженер Дмитро в Києві пише конфіг для файрвола.
    
3. CI/CD робот в дата-центрі Amazon у Вірджинії повинен зібрати це разом і задеплоїти.
    

Комп'ютери Васі й Дмитра вимкнені вночі. Як робот забере код? Через **Remote Repository** (Віддалене сховище — GitHub, GitLab, Bitbucket або AWS CodeCommit). Це хмарний сервер, який є **Єдиним Джерелом Правди (Single Source of Truth)**. Твій ноутбук — це просто тимчасовий термінал для введення символів.

### Анатомія понять (Руйнуємо міфи новачків)

1. **Що таке Remote насправді?** Новачки думають, що це якась надскладна хмарна субстанція. Ні. Це _абсолютно така сама папка `.git`_, як у тебе на Linux, просто вона лежить на чужому комп'ютері, до якого ти підключаєшся по мережі.
    
2. **Що таке загадковий `origin`?** Коли джун пише `git push origin master`, він думає, що `origin` — це магічне заклинання Гіта.
    
    **Розкриваю секрет:** `origin` — це просто _нікнейм_ (псевдонім). Розробникам Git було ліньки щоразу писати в терміналі:
    
    `git push https://github.com/kostenko_dmytro/super-mega-project.git master`
    
    Тому вони сказали: _"Давайте назвемо цю довжелезну лінку коротким словом `origin` (Джерело)"_. Ти можеш назвати свій віддалений сервер хоч `git remote add babulya https://...`, і тоді будеш писати `git push babulya master`. Але `origin` — це світовий DevOps-стандарт.
    
3. **Що таке `upstream`?** Це буквально "течія вгору". Це зв'язок між твоєю локальною гілкою `master` на ноутбуці та гілкою `master` на GitHub. Коли зв'язок встановлено, Git знає: _"Ага, локальний master Дмитра прив'язаний до хмарного master"_.

# КРИТИЧНИЙ БЛОК: Автентифікація (Чому паролі померли)

У 2021 році GitHub вимкнув вхід за звичайним паролем. Якщо ти спробуєш запушити код, ввівши логін і пароль від свого акаунта, GitHub відповість: `403 Forbidden`.

DevOps-інженери використовують два шляхи:

1. **HTTPS + Personal Access Token (PAT)** _(Працюємо з ним сьогодні)_.
    
    Замість пароля ти даєш Гіту довгий штрих-код типу `ghp_xYz123AbC...`. Його плюс: токену можна дати права "тільки читати репозиторій" або "тільки пушити", і якщо його вкрадуть — ти просто натискаєш кнопку _Revoke_, і хакер лишається з носом, а твій основний пароль від GitHub в безпеці.
    
2. **SSH-ключі (Асиметричне шифрування)** _(Справжній еталон в компаніях)_.
    
    На твоєму Linux генерується пара цифрових ключів: **Приватний** (лежить у тебе в закритій папці `~/.ssh/id_rsa` і нікуди не передається) та **Публічний** (текст, який ти вставляєш в налаштування GitHub). Коли ти робиш `push`, GitHub кидає твоєму Linux математичну загадку, яку може розв'язати _тільки_ власник Приватного ключа. Розв'язав за 0.001 сек — проходь.
    

# АНАТОМІЯ КОМАНД

### 1. Перегляд підключених "хмар"

Bash

```
git remote -v
```

- **Що робить:** Показує список прив'язаних інтернет-адрес. Прапорець `-v` (`verbose`) означає "розгорнуто" (показати точний URL). Якщо вивід порожній — твій репозиторій сліпий і не знає про інтернет.
    

### 2. Прив'язка локальної папки до GitHub

Bash

```
git remote add origin https://github.com/твоє_іно/назва_репо.git
```

- **Синтаксис:** `створи зв'язок` -> `назви його origin` -> `ось посилання`.
    

### 3. Перший запуск у космос (Push)

Bash

```
git push -u origin master
```

- **`push`** — Штовхнути.
    
- **`-u`** _(скорочення від `--set-upstream`)_ — **Найважливіший прапорець першого разу**. Він каже Гіту: _"Надішли гілку master в origin, І ЗАПАМ'ЯТАЙ ЦЕЙ ШЛЯХ"_. Коли ти напишеш цю команду один раз, завтра ти зможеш писати просто `git push`, і Linux сам зрозуміє, куди штовхати.
    

### 4. Питання на $5000: `git fetch` проти `git pull`

Це питання ставлять на **кожному** першому співбесідуванні Junior/Middle DevOps. Різниця фундаментальна:

- **`git fetch` (Безпечний розвідник):** Йде в інтернет, завантажує всі нові коміти твоїх колег у приховану пам'ять твого комп'ютера, **АЛЕ НЕ ЗМІНЮЄ ЖОДНОГО ТВОЄГО ФАЙЛУ**. Ти можеш зробити `git log origin/master` і подивитися, що там написав Вася, переконатися, що він не зламав код, і тільки потім вручну влити це в себе.
    
- **`git pull` (Хірургічний агресор):** Це комбо-команда двох дій: **`git fetch` + `git merge`**. Вона йде в інтернет, забирає код колег і **миттєво, силою** намагається вклеїти його в твої відкриті файли. Якщо ти в цей момент писав код у тому самому рядку — ти отримуєш `Merge Conflict` прямо посеред робочого дня.
    

> _Правило Senior інженера: Спочатку роби `fetch`, дивись очима, потім роби `merge`. Командою `pull` користуйся лише тоді, коли точно знаєш, що твоя локальна гілка пуста._

# ДЕМОНСТРАЦІЙНІ ПРИКЛАДИ

### Рівень 1: Beginner (Пуш готового проєкту)

Bash

```
# Ти створив проєкт локально, а потім вирішив закинути на GitHub
git remote add origin https://github.com/kostenko/my-api.git
git branch -M main  # Примусово перейменовуємо master в main (вимога GitHub)
git push -u origin main
```

### Рівень 2: Junior DevOps (Ранковий ритуал на роботі)

Bash

```
# Прийшов в офіс о 9:00. Колеги вночі щось деплоїли.
git fetch origin                  # Підтягнув новини з хмари
git status                        # Бачиш: "Your branch is behind by 3 commits"
git diff master origin/master     # Дивишся через термінал, що саме вони змінили
git merge origin/master           # Безпечно оновив свій локальний код
```

### Рівень 3: Production (Автентифікація робота в скрипті деплою)

CI/CD скрипт на чисту віртуальну машину AWS не має браузера, щоб ввести логін. Він клонує приватний репозиторій підставляючи токен прямо в посилання:

Bash

```
git clone https://oauth2:ghp_AbCdEf123456789@github.com/company-name/private-billing-svc.git .
```

# ТИПОВІ ПОМИЛКИ ТА ЇХ ДЕБАГ

1. **`error: failed to push some refs to... Updates were rejected because the remote contains work that you do not have locally.`**
    
    - **Що сталося:** Колега запушив на GitHub швидше за тебе. На GitHub версія №5, а ти намагаєшся поверх неї штовхнути свою версію №4. Git захищає історію.
        
    - **Лікування:** Спочатку затягни чужий код (`git pull`), виріши можливі конфлікти локально, зроби коміт об'єднання, і тільки тоді знову `git push`.
        
2. **`fatal: remote origin already exists.`**
    
    - **Що сталося:** Ти помилився лінкою, і вдруге пишеш `git remote add origin ...`. Git каже: "Ім'я origin вже зайняте!".
        
    - **Лікування:** Не додавай новий, а _зміни_ старий:
        
        `git remote set-url origin https://нова_правильна_силка.git`
